## 1. 🔍 데이터베이스 인덱스(Index) 개요 및 필요성

### 1.1 인덱스란?

인덱스는 데이터베이스 테이블의 검색 속도를 향상시키기 위해 특정 컬럼의 값을 **정렬하여 별도의 저장 공간에 관리하는 자료구조**입니다. 책 맨 뒤의 '찾아보기(색인)'와 동일한 역할을 합니다.

### 1.2 성능 향상 메커니즘

1. **탐색 복잡도 개선 ($\mathcal{O}(N) \rightarrow \mathcal{O}(\log N)$)**
   - **Full Table Scan ($\mathcal{O}(N)$):** 인덱스가 없으면 조건에 맞는 데이터를 찾기 위해 테이블의 첫 행부터 끝 행까지 모두 확인해야 합니다.
   - **Index Scan ($\mathcal{O}(\log N)$):** 정렬된 B-Tree 구조를 타고 내려가 탐색 횟수를 극적으로 줄입니다. (예: 1,000만 건 데이터 탐색 시 약 23~24회 비교로 수렴)

2. **디스크 I/O(입출력) 감소**
   - DB 성능의 가장 큰 병목은 디스크 접근(Disk Read)입니다.
   - 인덱스를 사용하면 전체 테이블 페이지를 디스크에서 읽어올 필요 없이, 데이터의 주소값(Row ID 또는 Primary Key)이 저장된 최소한의 인덱스 리프 노드만 접근하므로 I/O 발생이 획기적으로 줄어듭니다.

3. **정렬(Ordering) 및 연산 최적화**
   - 인덱스 키는 이미 정렬된 상태를 유지하므로 `ORDER BY` 연산 시 별도의 메모리/디스크 정렬 작업(Filesort)을 생략할 수 있습니다.
   - `GROUP BY` 및 범위 검색(`BETWEEN`, `>`, `<`) 시 정렬된 연속 메모리를 순차적으로 읽기만(Sequential Read) 하면 되므로 연산 효율이 높습니다.

4. **조인(JOIN) 성능 최적화**
   - 외래키(FK) 컬럼에 인덱스가 존재할 때 부모-자식 테이블 조인 처리 속도가 대폭 향상됩니다.

5. **커버링 인덱스(Covering Index)**
   - 쿼리에 필요한 모든 컬럼이 인덱스 자체에 포함된 경우, 실제 테이블 데이터 레코드를 찾아가는 Random I/O 과정을 완전히 생략하여 최고 속도를 제공합니다.

### 1.3 Full Table Scan vs Index Scan 비교

```text
[ Full Table Scan : O(N) ]
Row 1 ---> Row 2 ---> Row 3 ---> ... ---> Row 10,000,000 (전체 전수 조사)

[ Index Range Scan : O(log N) ]
Root Node ---> Internal Node ---> Leaf Node (원하는 범위만 빠르게 핀포인트 탐색)
```

## 2. 🧠 인덱스의 내부 자료구조: B-Tree & B+Tree

### 2.1 B-Tree를 인덱스 표준으로 사용하는 이유

DB 엔진이 이진 탐색 트리(BST), Red-Black 트리 등이 아닌 B-Tree (및 B+Tree)를 채택한 핵심 이유는 **하드웨어 저장장치(디스크/SSD)의 Block I/O 특성** 때문입니다.

```text
[ 이진 트리 (Binary Tree) ]
페이지 1 (16KB) ──> [ 노드 1개 (수십 바이트만 사용) ] ──> 디스크 공간/대역폭 낭비

[ B-Tree ]
페이지 1 (16KB) ──> [ 노드 1개 (수백 개의 키값 + 자식 포인터로 16KB 채움) ] ──> I/O 효율 100%
```

1. **트리의 높이(Height) 최소화:**
   - 디스크에서 데이터 1회 Read = 트리 높이 $H$만큼 I/O 발생.
   - 이진 트리는 자식이 2개이므로 높이가 $\log_2 N$으로 높습니다. (1,000만 건 데이터 $\approx$ 높이 24)
   - B-Tree는 자식을 수백 개 가져 높이가 $\log_M N$으로 낮아집니다. (1,000만 건 데이터 $\approx$ 높이 3)

2. **페이지(Page) 단위 입출력과의 부합:**
   - DB 엔진은 디스크에서 **16KB(기본 페이지 크기)** 단위로 읽습니다.
   - B-Tree는 "1개 노드의 크기 = 1개 디스크 페이지 크기"가 되도록 설계하여, 단 1회의 디스크 I/O로 수백 개의 키를 RAM 메모리로 일괄 캐싱합니다.

3. **In-Memory 이진 탐색 활용:**
   - 16KB 노드 하나를 RAM에 올린 뒤 노드 내부의 수백 개 키를 비교하는 연산은 RAM 처리이므로 시간이 사실상 $0$에 가깝습니다.

### 2.2 Hash Index vs B+Tree Index 비교

```text
                  [ Root Node ]
                     | 50 |
                   /        \
       [ Internal Node ]   [ Internal Node ]
          | 20 | 35 |         | 65 | 80 |
         /     |    \        /     |    \
      Leaf    Leaf   Leaf   Leaf   Leaf   Leaf  <-- Linked List 구조로 연결 (범위 검색 최적화)
    [10..]  [20..] [35..] [50..] [65..] [80..]
```

- **Hash Index:** 등가 비교(`=`)에는 $\mathcal{O}(1)$로 매우 빠르지만, 범위 검색(`WHERE age BETWEEN 20 AND 30`)이나 정렬(`ORDER BY`)이 불가능합니다.
- **B+Tree Index:** 모든 Leaf Node가 **Doubly Linked List**로 연결되어 있어 범위 검색과 정렬 조회가 매우 효율적입니다.

### 2.3 B-Tree의 정의, 성질 및 내부 연산 메커니즘

#### 1) B-Tree의 정의 및 성질 (최소 차수 $t \ge 2$)
- **키 개수 제한:** 루트 노드를 제외한 모든 노드는 최소 $t - 1$개, 최대 $2t - 1$개의 키를 가집니다. (루트는 최소 1개)
- **자식 노드 개수:** 내부 노드의 자식 수 = `(자신이 가진 키 개수) + 1`개.
- **완벽한 높이 균형:** 모든 리프 노드는 항상 동일한 깊이(Level)에 위치합니다.

#### 2) 탐색 복잡도 바로잡기 ($\mathcal{O}(\log N)$)
- **오해:** "트리를 내려가는 $\mathcal{O}(\log N)$ $\times$ 노드 내 선형 탐색 $\mathcal{O}(N)$ = $\mathcal{O}(N \log N)$이다?"
- **정정:** 노드 내부의 키 개수는 전체 데이터 $N$과 상관없는 고정된 상수 값(최대 $2t-1$개)입니다. 따라서 노드 내부 탐색은 $\mathcal{O}(1)$이며, 전체 탐색 복잡도는 $\mathcal{O}(\log N)$입니다.

#### 3) 삽입(Insert)과 분할(Split) 동작 과정
데이터 삽입 시 노드가 꽉 차면($2t - 1$개), 선제적 분할(Preemptive Split)이 발생합니다.

- **예시 ($t = 2$, 노드당 최대 3개 키):**
  1. `[10, 20, 30]` 상태에서 `40` 삽입 시도.
  2. 노드가 꽉 찼으므로 중앙값(Median) `20`을 부모 노드로 올려보냄.
  3. 기존 노드는 `20`을 기준으로 왼쪽 `[10]`과 오른쪽 `[30]` 노드로 split됨.
  4. `40`은 오른쪽 노드 `[30]` 뒤에 붙어 `[30, 40]`이 됨.

- **루트 노드가 터지는 경우 (트리 레벨 증가):**
  - 루트 노드가 분할될 때도 **중앙값 딱 1개만** 새로 생성되는 최상위 루트 노드로 올라갑니다.
  - B-Tree 속성상 루트 노드는 예외적으로 **최소 1개의 키**만 가져도 합법입니다.
  - 루트에 키 1개가 새로 얹어지면서 트리의 전체 레벨(높이)이 위로 1단계 확장됩니다. (트리는 밑으로 자라는 것이 아니라 위로 자람)

#### 4) 자식 포인터($C_1 \sim C_n$) 분할 기준
분할 전 노드의 키 사이사이에 존재하던 자식 포인터 범위는 중앙값 `M`을 기준으로 분리될 때, **기존에 담당하던 값의 범위(Range) 그대로** 새로 생성된 좌/우 부모 노드의 자식 리스트로 절반씩 재할당됩니다.

#### 5) 삭제(Delete) 연산 및 재배치/병합
삭제 후 노드의 키 개수가 최소 조건($t - 1$) 밑으로 떨어지면 아래 연산이 수행됩니다.

1. **형제 노드에서 빌려오기 (Redistribute/Borrow):** 풍족한 형제 노드가 있다면 형제의 키를 부모로 올리고, 부모의 키를 모자란 노드로 내려받아 최소 개수를 채웁니다.
2. **병합 (Merge):** 형제 노드도 최소 키만 갖고 있다면 `(내 노드 + 부모 키 1개 + 형제 노드)`를 하나로 결합합니다. 이로 인해 부모 노드의 키가 1개 줄어들며, 위쪽 레벨로 연쇄 병합(Cascade Merge)이 올라갈 수 있습니다.
3. **내부 노드 삭제:** 삭제할 키가 중간 노드에 있다면, 왼쪽 자식의 가장 큰 값(Predecessor) 또는 오른쪽 자식의 가장 작은 값(Successor)과 값을 교체한 후 리프 노드 삭제로 전환합니다.

## 3. ⚙️ 디스크 및 페이지 내부의 물리적 구조 (하이브리드 배치)

B-Tree는 단순히 배열이나 연결 리스트 하나만 사용하지 않고, 목적에 따라 여러 자료구조를 혼합하여 물리 디스크에 저장합니다.

```text
[ 전체 DB 파일 ]: 페이지(16KB)들의 1차원 연속 배열 (Page ID로 포인팅)

[ 페이지 1개 내부 (16KB) 레이아웃 ]
┌────────────────────────────────────────────────────────┐
│ Page Header                                            │
├────────────────────────────────────────────────────────┤
│ 레코드 1 ──(next_record)──> 레코드 2 ──(next)──> ...     │  <-- 단방향 연결 리스트
├────────────────────────────────────────────────────────┤
│ Free Space                                             │
├────────────────────────────────────────────────────────┤
│ [ Slot 0 ] | [ Slot 1 ] | [ Slot 2 ] | ...             │  <-- Page Directory (슬롯 배열)
└────────────────────────────────────────────────────────┘
  (페이지 맨 끝 영역에 역순으로 쌓임)
```

### 3.1 전체 DB 파일: 페이지 배열 + Page ID
- DB 파일 전체는 **16KB 크기의 페이지들이 이어진 1차원 배열**입니다.
- B-Tree의 자식 포인터는 메모리 주소가 아닌 자식 페이지 번호(Page ID / Offset)를 저장하여 디스크 내 해당 위치(`File_Buffer[Page_ID]`)로 즉시 접근합니다.

### 3.2 페이지 내부 레코드: 단방향 연결 리스트 (Singly Linked List)
- 페이지 내부 레코드들은 헤더의 `next_record` 오프셋 포인터를 통해 **단방향 연결 리스트**로 묶여 있습니다.
- **이유:** 중간에 레코드가 `INSERT` 될 때, 단순 배열처럼 모든 메모리를 뒤로 밀어내는 **메모리 복사(Memory Shift) 비용을 방지**하기 위함입니다.

### 3.3 페이지 내부 탐색: 슬롯 배열 (Page Directory)
- 연결 리스트만 사용하면 페이지 내부 탐색 시 $\mathcal{O}(N)$의 시간이 걸리는 단점이 있습니다.
- 이를 해결하기 위해 페이지 맨 끝(End)에 4~8개 레코드마다 1개씩 대표 포인터를 모아둔 1차원 연속 배열(Page Directory)을 둡니다.
- **동작:** 슬롯 배열은 메모리가 연속되어 있으므로 `mid = (low + high) / 2` 방식으로 **$\mathcal{O}(\log N)$ 이진 탐색**을 수행해 근접 슬롯을 찾은 뒤, 해당 슬롯부터 단방향 연결 리스트를 몇 칸만 타고 들어가 데이터를 찾아냅니다.

### 3.4 리프 페이지 간 연결: 이중 연결 리스트 (Doubly Linked List)
- B+Tree의 모든 최하단 리프 페이지들은 이전 페이지 번호(`FIL_PAGE_PREV`)와 다음 페이지 번호(`FIL_PAGE_NEXT`) 포인터를 통해 **이중 연결 리스트**로 묶여 있습니다.
- **이유:** `ORDER BY ASC` / `DESC` 양방향 순차 스캔 및 범위 검색(`BETWEEN`) 시 트리를 재탐색하지 않고 옆 페이지로 계속 이동하며 다량의 데이터를 빠르게 읽어오기 위함입니다.

### 3.5 딜리트 마크(Delete Mark)와 수정/탐색 메커니즘

#### 1) 딜리트 마크(Delete Mark)란?
B-Tree 리프 노드에 저장된 개별 레코드 헤더(Header) 영역의 `info_bits`에 존재하는 1비트(Bit) 크기의 플래그(`REC_INFO_DELETED_FLAG`)입니다.

```text
┌─────────────────────────────────────────────────────────────┐
│                    B-Tree Leaf Record                       │
├──────────────────────────────┬──────────────────────────────┤
│    Record Header (5 Bytes)   │     Index Key & Payload      │
│  [ info_bits | ... | ptr ]   │     (e.g., store_id, PK)    │
└──────────────┬───────────────┴──────────────────────────────┘
               │
               ▼
  info_bits 내 DELETED_FLAG Bit를 0에서 1로 변경
```

#### 2) UPDATE 및 DELETE 수행 시 물리적 동작
1. **UPDATE (인덱스 키 수정 시):**
   - 기존 위치의 인덱스 레코드 헤더 비트를 `1`로 수정 (**Delete Mark**).
   - 정렬된 새로운 위치를 찾아 B-Tree 리프 노드에 새 레코드를 **Insert**.
2. **수명 주기 (Purge Thread):**
   - Delete Mark가 찍힌 데이터는 '유령(Tombstone) 레코드' 상태로 남아 MVCC(다중 버전 동시성 제어) 읽기를 보장합니다.
   - 트랜잭션이 종료되면 백그라운드 **Purge Thread**가 실제 물리적 연결을 끊고 공간을 Free Space로 회수합니다.
3. **공간 재활용 (Resurrection):**
   - Purge 쓰레드가 지우기 전 동일한 키로 `INSERT`가 들어오면, 새 노드를 만들지 않고 Delete Mark 비트만 `0`으로 되돌려 기존 자리를 재활용합니다.

#### 3) Delete Mark가 존재할 때의 B-Tree 탐색
- **내부 노드(Branch/Root):** 리프 노드에서 Delete Mark가 찍혔더라도, 내부 노드의 키는 길잡이(Guide) 역할을 위해 그대로 유지됩니다. 탐색 알고리즘은 이를 무시하고 포인터를 타고 내려갑니다.
- **리프 노드(Leaf):** 목적지 레코드에 도달했을 때 비트 값이 `1`이면 존재하지 않는 데이터로 판단하고 결과 집합에서 스킵(Skip)합니다.

## 4. 📌 인덱스 종류 및 구조적 차이

### 4.1 Clustered Index vs Secondary Index

| 구분 | 클러스터드 인덱스 (Clustered Index) | 세컨더리 인덱스 (Secondary Index) |
| :--- | :--- | :--- |
| **기준** | 테이블당 **단 1개** 존재 (주로 Primary Key) | 테이블당 **여러 개** 생성 가능 |
| **정렬** | 실제 리프 노드에 **실제 레코드 데이터가 물리적으로 정렬**되어 저장됨 | 리프 노드에 **PK 값(또는 포인터)**이 저장됨 |
| **탐색 방식** | 인덱스 리프 노드 = 실제 데이터 레코드 | 세컨더리 인덱스 탐색 $\rightarrow$ PK 획득 $\rightarrow$ 클러스터드 인덱스 재탐색 (Double Lookup) |

### 4.2 복합 인덱스 (Composite Index)와 Leftmost Prefix 법칙

두 개 이상의 컬럼을 묶어서 생성하는 인덱스입니다.

```sql
CREATE INDEX idx_orders_store_created ON orders (store_id, created_at);
```

- **Leftmost Prefix 법칙**: 인덱스의 첫 번째 컬럼(`store_id`)이 `WHERE` 절에 포함되어야만 인덱스가 정상 작동합니다.
  - `WHERE store_id = 1 AND created_at >= '2026-08-01'` $\rightarrow$ **인덱스 작동 (O)**
  - `WHERE store_id = 1` $\rightarrow$ **인덱스 작동 (O)**
  - `WHERE created_at >= '2026-08-01'` $\rightarrow$ **인덱스 미작동 (X / Full Table Scan)**

### 4.3 단일 인덱스 N개 vs 결합 인덱스 1개 비교

두 개의 단일 인덱스 `(id)`, `(created_at)`을 각각 만드는 것과 **결합 인덱스 `(id, created_at)` 하나를 만드는 것**의 핵심 차이는 "두 컬럼을 동시에 조건으로 조회하거나 정렬할 때의 성능과 효율성"에 있습니다.

#### 결합 인덱스의 4가지 핵심 장점

1. **다중 조건 검색 시 단 한 번의 B-Tree 탐색 (정밀 타격):**
   - **쿼리:** `WHERE id = 10 AND created_at >= '2026-08-01'`
   - **단일 인덱스 2개:** DB 옵티마이저는 보통 1개만 선택하여 `id = 10` 1만 건을 찾은 뒤, 디스크 원본 페이지에서 `created_at` 필터링 (Random I/O 1만 번 발생).
   - **결합 인덱스 1개:** B-Tree 자체가 `(id, created_at)` 조합으로 정렬되어 있으므로, 시작 위치로 바로 점프하여 필요한 범위만 딱 읽고 종료합니다.

2. **정렬 연산(Filesort)의 완전한 제거:**
   - **쿼리:** `WHERE id = 10 ORDER BY created_at DESC`
   - **단일 인덱스 2개:** `id` 인덱스로 추출 후 메모리/디스크에서 별도 정렬(Filesort) 수행.
   - **결합 인덱스 1개:** `id = 10` 그룹 내에서 `created_at`이 **물리적으로 정렬된 상태**이므로 정렬 없이 역순으로 읽어 즉시 반환.

3. **커버링 인덱스(Covering Index)를 통한 테이블 Access 최소화:**
   - **쿼리:** `SELECT id, created_at FROM orders WHERE id = 10 AND created_at >= '2026-08-01'`
   - **결합 인덱스 1개:** 조회 컬럼이 인덱스 리프 페이지 안에 전부 존재하여, 원본 데이터 페이지 조회를 생략하고 인덱스만으로 완결 (Random Disk I/O = 0).

4. **쓰기(CUD) 오버헤드 감소:**
   - 단일 인덱스 2개는 CUD 시 2개의 B-Tree를 모두 수정/밸런싱해야 하나, 결합 인덱스는 1개의 B-Tree만 수정하면 됩니다.

#### 한눈에 보는 비교 표

| 검색 조건 및 동작 | 단일 인덱스 2개 `(id)`, `(created_at)` | 결합 인덱스 1개 `(id, created_at)` |
| --- | --- | --- |
| `WHERE id = ?` | 인덱스 탐색 가능 | **인덱스 탐색 가능** |
| `WHERE created_at = ?` | 인덱스 탐색 가능 | **인덱스 탐색 불가** *(Leftmost Rule 위배)* |
| `WHERE id = ? AND created_at = ?` | 1개 인덱스 탐색 후 나머지 필터링 *(I/O 높음)* | **단 한 번의 B-Tree 탐색으로 정밀 타격** |
| `WHERE id = ? ORDER BY created_at` | 별도 정렬 연산 필요 *(Filesort)* | **이미 정렬되어 있어 즉시 반환** |
| **CUD 쓰기 오버헤드** | B-Tree 2개 업데이트 | **B-Tree 1개만 업데이트** |

### 4.4 커버링 인덱스 (Covering Index)

쿼리에 필요한 모든 컬럼이 인덱스 자체에 포함되어 있어, **실제 테이블 데이터 블록 접근(Random I/O) 없이 인덱스 노드만으로 쿼리를 완결**하는 최고 성능의 최적화 기법입니다.

## 5. ⚖️ 인덱스 생성과 CUD 비용 (Trade-off)

### 5.1 CUD 작업 시 발생하는 오버헤드

인덱스는 조회(SELECT) 속도를 올리는 대신 쓰기/수정/삭제 작업 시 추가 비용이 발생합니다.

- **INSERT:** 기본 테이블에 행을 추가하는 것 외에 인덱스 B-Tree 상의 정렬된 위치를 찾아 노드를 추가하고, 필요시 노드 분할(Split) 연산을 수행합니다.
- **DELETE:** 인덱스 노드에서 해당 레코드를 삭제 처리(Delete Mark)하고, 노드의 최소 키 개수가 미달할 경우 재배치/병합 연산을 수행합니다.
- **UPDATE:** 인덱스 키 컬럼이 변경되면 기존 위치의 키를 삭제 처리(Delete Mark)하고 새 위치에 삽입(Insert)하는 2단계 연산이 발생합니다.

### 5.2 읽기/쓰기 비대칭성 분석 (예: `orders(store_id, created_at)`)

결합 인덱스 `(store_id, created_at)` 환경을 기준으로 한 읽기/쓰기 비대칭성 분석:

- **Write (주문 생성):** 쓰기 시 B-Tree 추가 연산 비용은 $\mathcal{O}(\log N)$으로 수 밀리초(ms) 이하의 작은 오버헤드가 발생합니다.
- **Read (주문 조회):** 포스기, 점주 앱 등에서 실시간으로 발생하는 최신 주문 조회 시, 정렬 연산 없이 **"해당 매장의 최신 데이터 위치"로 즉시 접근하여 Early Stop** 처리를 수행합니다.
- **결론:** 수백~수천 번 실행되는 조회에서 수십 초의 Full Scan 지연을 수 밀리초로 줄여주므로, CUD 오버헤드를 압도하는 성능 이득을 제공합니다.

## 6. 🚨 교과서 이론 vs 실무 현장의 차이점 & 튜닝 실무

### 6.1 [이론 vs 실무 1] "인덱스를 많이 걸수록 조회가 무조건 빨라진다."
- **실무의 현실 (No Free Lunch):**
  - **쓰기 성능 저하 (Write Penalty):** `INSERT`, `UPDATE`, `DELETE` 발생 시, 테이블뿐만 아니라 **모든 인덱스의 B+Tree 구조를 재정렬**해야 합니다.
  - **페이지 분할 (Page Split):** B+Tree 노드가 가득 차면 노드를 분할하는 비싼 디스크 I/O 비용이 발생합니다.
  - **메모리(Buffer Pool) 낭비:** 인덱스도 물리적 용량을 차지하므로, 쓸데없는 인덱스가 많으면 정작 필요한 데이터가 RAM 메모리에서 밀려납니다.
  - 👉 **실무 지침:** 테이블당 인덱스는 보통 **3~5개 이내**로 최소화해야 합니다.

---

### 6.2 [이론 vs 실무 2] "인덱스를 만들어 두면 DB가 알아서 항상 인덱스를 쓴다."
- **실무의 현실 (Cost-Based Optimizer & Cardinality):**
  - DB의 **Cost-Based Optimizer(CBO)**는 데이터의 통계 정보(Statistics)를 바탕으로 실행 계획을 세웁니다.
  - **카디널리티(Cardinality / 선택도) 문제:**
    - 중복도가 높은 컬럼(예: 성별 `M/F`, 주문 상태 `PAID/CANCELLED`)에 인덱스를 걸면, Optimizer는 인덱스를 거쳐 테이블을 랜덤 I/O 하는 것보다 **Full Table Scan이 더 빠르다고 판단하여 인덱스를 무시**합니다.
  - 👉 **실무 지침:** 인덱스는 **카디널리티가 높은(중복도가 적고 유일한 값에 가까운)** 컬럼(예: `user_id`, `order_no`)에 우선적으로 걸어야 합니다.

---

### 6.3 [이론 vs 실무 3] "WHERE 절에 인덱스 컬럼을 넣으면 무조건 적용된다."
- **실무의 현실 (인덱스 무효화 5대 패턴):**
  개발자의 실수로 인덱스가 무효화되는 대표적인 실무 사례들입니다.

| 인덱스 무효화 원인 | 잘못된 쿼리 (인덱스 불응) | 올바른 쿼리 튜닝 (인덱스 활용) |
| :--- | :--- | :--- |
| **컬럼의 가공/함수 사용** | `WHERE YEAR(created_at) = 2026` | `WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'` |
| **컬럼의 산술 연산** | `WHERE price * 0.9 < 10000` | `WHERE price < 10000 / 0.9` |
| **앞부분 와일드카드 LIKE** | `WHERE name LIKE '%버거'` | `WHERE name LIKE '성수%'` (후방 와일드카드만 가능) |
| **암묵적 형변환 (Implicit Type)**| `WHERE phone = 01012345678` (숫자 vs TEXT)| `WHERE phone = '01012345678'` |
| **`OR` 조건절 사용** | `WHERE store_id = 1 OR category = '메인'` | `UNION`으로 분리하거나 각각에 맞는 인덱스 설계 |

---

### 6.4 [이론 vs 실무 4] "한번 만든 인덱스는 영원히 고성능을 유지한다."
- **실무의 현실 (인덱스 파편화 & 단편화):**
  - 지속적인 `UPDATE`와 `DELETE`가 일어나면 B+Tree 노드에 빈 공간(Hole)이 생기며 **인덱스 단편화(Index Fragmentation)**가 진행됩니다.
  - 실무에서는 정기적으로 인덱스 크기와 단편화율을 모니터링하고 `REINDEX` 또는 `OPTIMIZE TABLE` 명령을 통해 인덱스를 재건축(Rebuild)해야 합니다.

## 7. 🍽️ 실무 인덱스 설계 사례: 테이블 오더 시스템

### 7.1 시나리오: 매장 관리자 POS 화면의 "오늘 주문 목록" 조회

- **요구사항**: 특정 매장(`store_id = 5`)의 오늘 주문 내역을 최근 순으로 조회.
- **SQL 쿼리**:
  ```sql
  SELECT id, table_number, total_amount, status, created_at
  FROM orders
  WHERE store_id = 5 AND created_at >= '2026-08-03 00:00:00'
  ORDER BY created_at DESC;
  ```

### 7.2 인덱스 구성에 따른 성능 비교

1. **인덱스가 없을 때 (Full Table Scan):**
   - 1,000만 건 중 1,000만 건을 모두 읽음 $\rightarrow$ **소요 시간: 3.5초 (서비스 장애 수준)**

2. **`store_id` 단일 인덱스만 있을 때:**
   - `store_id = 5`인 데이터 10,000건을 추출한 뒤, 메모리에서 10,000건을 다시 정렬(`Using filesort`) $\rightarrow$ **소요 시간: 0.15초**

3. **`(store_id, created_at DESC)` 복합 인덱스 설계 시 (최적의 인덱스):**
   - **인덱스 생성**:
     ```sql
     CREATE INDEX idx_orders_store_created ON orders (store_id, created_at DESC);
     ```
   - **효과**:
     - `store_id = 5` 조건을 탐색함과 동시에, 이미 B+Tree 내부에서 `created_at` 순으로 정렬되어 있으므로 **정렬 연산(Sort)을 완전히 생략(Avoid Sorting)**하고 핀포인트로 읽어옴.
     - $\rightarrow$ **소요 시간: 0.001초 (1ms 이하 즉시 응답)**

## 8. 📊 최종 요약 구조표 & 인덱스 튜닝 5대 수칙

### 8.1 인덱스 및 디스크 내부 구조 최종 요약표

| 구분 | 적용 위치 / 대상 | 채택된 자료구조 | 핵심 목적 및 효과 |
| --- | --- | --- | --- |
| **전체 인덱스 트리** | 디스크 / 메인 메모리 | **B+Tree** | 디스크 I/O 최소화 ($\mathcal{O}(\log N)$ 탐색 보장) |
| **디스크 파일 관리** | DB 전체 데이터 파일 | **페이지 배열 + Page ID** | 16KB 단위 블록 입출력 최적화 |
| **페이지 내부 레코드** | 1개 페이지(16KB) 내부 | **단방향 연결 리스트** | 레코드 삽입/삭제 시 메모리 이동(Shift) 최소화 |
| **페이지 내부 탐색** | 페이지 디렉토리 | **슬롯 배열 (Sparse Array)** | 페이지 내부 레코드 대상 **$\mathcal{O}(\log N)$ 이진 탐색** 지원 |
| **리프 페이지 연결** | B+Tree 최하단 리프 노드들 | **이중 연결 리스트** | 양방향 범위 스캔 (`ASC`/`DESC`) 최적화 |
| **레코드 삭제 표시** | 레코드 헤더 (`info_bits`) | **1비트 플래그 (Delete Mark)** | 빠른 물리 연산, MVCC 구현, Purge를 통한 공간 재활용 |

### 8.2 인덱스 튜닝 5대 핵심 수칙

1. **카디널리티가 높은(중복도가 낮은) 컬럼**에 우선적으로 인덱스를 생성하라.
2. **복합 인덱스 생성 시 순서가 핵심**이다 (`WHERE` 절의 등가 비교 `=` 컬럼 $\rightarrow$ 범위 비교 `<, >` 또는 정렬 컬럼 순).
3. **`WHERE` 절에서 컬럼을 가공하지 마라** (함수, 산술 연산, 암묵적 형변환 금지).
4. **쓰기(INSERT/UPDATE/DELETE) 연산이 잦은 테이블은 인덱스 개수를 최소화**하라.
5. **실제 `EXPLAIN` (실행 계획)을 통해 인덱스를 타는지 반드시 타당성을 검증**하라.

## 9. 💾 외장 메모리 자료구조 (External Memory Data Structures)

컴퓨터 공학에서는 디스크 I/O를 최소화하기 위해 설계된 자료구조들을 **외장 메모리 자료구조(External Memory Data Structures)** 또는 **I/O 효율적 자료구조(I/O-Efficient Data Structures)**라고 부릅니다.

메모리(RAM)와 CPU 연산 중심의 일반 자료구조(레드-블랙 트리, 해시 테이블 등)와 달리, 디스크 I/O를 최소화하기 위해 **"CPU 연산이나 메모리 사용량을 희생하더라도 디스크 접근 횟수를 줄이는 전략"**을 취합니다.

### 9.1 대표적인 외장 메모리 자료구조

#### 1) B-Tree / B+Tree (높이를 낮춰 Disk Read 최소화)
- 일반적인 이진 탐색 트리(BST)는 노드당 자식이 2개라 트리의 높이가 $\mathcal{O}(\log_2 N)$이 됩니다. 데이터가 10억 개면 트리의 높이가 약 30이 되어 **최악의 경우 30번의 디스크 접근**이 필요합니다.
- **I/O 최적화 방식:**
  - 노드 하나(페이지)의 크기를 디스크 블록 단위(예: 4KB ~ 16KB)에 맞춰 극대화합니다.
  - 자식 노드의 개수(Branching Factor, $B$)를 수백~수천 개로 늘려 트리의 높이를 $\mathcal{O}(\log_B N)$으로 획기적으로 낮춥니다.
- **CPU 희생 점:**
  - 한 노드 안에 들어있는 수백 개의 키를 찾기 위해 노드 내부에서 **추가적인 CPU 이진 탐색 연산**을 수행합니다.
  - 하지만 CPU가 노드 안에서 백 번 비교하는 시간(나노초)보다, 디스크에서 페이지를 읽어오는 시간(밀리초)이 수십만 배 길기 때문에 CPU 연산을 늘리고 I/O를 최소화하는 것이 압도적으로 유리합니다.

#### 2) LSM-Tree (Log-Structured Merge-tree) (쓰기 I/O의 극대화)
B-Tree가 읽기 성능에 최적화되어 있다면, LSM-Tree는 랜덤 쓰기(Random Write)를 순차 쓰기(Sequential Write)로 변환하기 위해 CPU 및 읽기 성능을 희생하는 대표적인 자료구조입니다. (RocksDB, Cassandra, LevelDB 등의 기본 데이터 저장 엔진)
- **I/O 최적화 방식:**
  - 디스크에서의 **Random Write는 헤드 이동 및 블록 재경로 문제로 비효율적**입니다.
  - LSM-Tree는 쓰기 요청이 오면 무조건 메모리 버퍼(MemTable)에 모아두었다가, 디스크에 순차적(Sequential)으로만 일괄 저장(SSTable)합니다.
- **CPU 희생 점:**
  - **컴팩션(Compaction):** 디스크에 정렬되지 않은 채 쌓인 수많은 파일들을 주기적으로 읽어 중복을 제거하고 정렬·합병(Merge Sort)하는 **막대한 CPU 연산과 백그라운드 I/O**를 지속 수행합니다.
  - **읽기 희생:** 데이터를 찾을 때 여러 레이어의 SSTable을 뒤져야 하므로 읽기 연산 시 CPU 부담이 증가합니다.

#### 3) Bloom Filter + SSTable (무의미한 Disk I/O 차단)
LSM-Tree 같은 구조에서 디스크에 저장된 특정 키를 찾기 위해 병행 사용하는 확률적 자료구조입니다.
- **I/O 최적화 방식:**
  - "이 키가 디스크에 **확실히 없는지**"를 미리 판단해 줍니다.
  - 블룸 필터가 "없다"고 판단하면, **디스크 파일 자체를 읽지 않고 바로 I/O를 Skip**합니다.
- **CPU 희생 점:**
  - 비트 배열(Bit Array)에 대해 **여러 개의 해시 함수(Hash Function)를 계산하는 CPU 연산**을 수행합니다.
  - CPU가 해시 연산을 몇 번 더 하더라도, 단 한 번의 불필요한 디스크 읽기(Disk Read)를 방지하는 것이 전체 시스템 관점에서 훨씬 이득이기 때문입니다.

#### 4) Fractal Tree (B$\epsilon$-Tree) (메시지 버퍼링)
B-Tree의 단점인 랜덤 쓰기 성능을 개선한 자료구조입니다.
- **I/O 최적화 방식:**
  - B-Tree의 각 노드에 '메시지 버퍼(Buffer)'를 둡니다.
  - 데이터의 삽입/수정이 들어오면 즉시 해당 위치까지 트리를 파고 내려가서 디스크를 수정하는 대신, **부모 노드의 버퍼에 "이 데이터 수정할 것"이라는 메시지만 적어두고 즉시 리턴**합니다.
  - 버퍼가 가득 차면 일괄적으로 하위 노드로 메시지를 밀어냅니다(Batch Processing).
- **CPU 희생 점:**
  - 데이터를 조회할 때 트리의 노드뿐만 아니라 **각 노드의 버퍼에 대기 중인 변경 이력(메시지)까지 CPU가 합성/해석**해서 최종 값을 계산해야 합니다.

### 9.2 In-Memory vs External Memory 자료구조 핵심 비교

| 구분 | 일반 자료구조 (In-Memory) | 외장 메모리 자료구조 (Disk/I-O) |
| --- | --- | --- |
| **최적화 목표** | CPU 비교 횟수 / 메모리 사용량 최소화 | 디스크 블록(페이지) 접근 횟수 최소화 |
| **주요 트레이드오프** | $\mathcal{O}(1)$, $\mathcal{O}(\log N)$ 알고리즘 구현 | CPU 연산 추가(해싱, 컴팩션, 노드 내 탐색 등) |
| **설계 철학** | 메모리는 주소 지정(Byte) 단위 접근 | 디스크는 무조건 **블록(Block, 4KB~)** 단위 접근 |

> 💡 **핵심 원리:** "CPU 연산 1,000번~10,000번을 더 하더라도 디스크 헤드 한 번 안 움직이게 만드는 것"이 디스크 I/O 최적화 외장 메모리 자료구조들의 핵심 설계 원칙입니다.
